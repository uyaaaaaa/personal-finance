# 技術選定

## スコープ

本書は [要求定義](requirements.md) を上位文書とし、そこで定義された体験を実現する技術スタックと、機能の実現に不可欠な外部サービスを定義する。画面の設計は [デザイン要件定義](design-requirements.md) が定める。

以下は定義しない。

* インフラ構成（ホスティング先、CI、監視、IaC）。アプリケーションの成立と独立に差し替え可能であり、本書の選定を制約しないため、導入するコンポーネントごとの設定・スクリプトが担う
* 各コンポーネントの内部設計（データモデルの詳細、API のエンドポイント定義）。実装とスキーマ・テストが担う

## 選定方針

初期フェーズの検証は失敗の早期検出を目的とする（要求定義「初期フェーズの検証」）。これを受けて、選定は次の2つを基準とする。

* **検証開始までの速度を優先する**。作者が習熟済みの技術を選び、マネージドサービスで代替できる要素は自作しない
* ただし、**メール解析ロジックとデータモデルは可搬性を確保する**。この2箇所には検証で得た知見（決済通知の書式、捕捉率の実態）が蓄積され、作り直すと検証結果ごと失われるためである。他の要素は、検証の結果に応じて捨てられることを許容する

## 全体構成

```
決済通知メール ─(ユーザーのメール環境で転送)→ Cloudflare Email Routing
    → Email Worker（固定パーサで店名・金額・日時を抽出） → D1

モバイルアプリ（Flutter）
    ⇄ API（Cloudflare Workers + Hono） ⇄ D1
    → Firebase Auth（Sign in with Apple / Google、ID トークンを API が検証）

毎晩の通知: 端末内のローカル通知（サーバー関与なし）
```

## モバイルアプリ

### Flutter

iOS / Android 両対応を単一コードベースで実現する。デザイン要件定義は画面の数・構成要素・状態・遷移を両 OS 共通と定めており、共通化された情報設計を1回だけ実装できる。OS の標準に委ねるとされた操作作法（数値キーボード、時刻ピッカー、戻る操作）は、Flutter の標準ウィジェットが各 OS の作法で提供する。

言語は Dart、リンタは Flutter 同梱の flutter_lints に custom_lint を加える。

### 主要パッケージ

| 用途 | パッケージ | 選定理由 |
|---|---|---|
| 状態管理 | Riverpod（+ riverpod_lint） | 本アプリの状態はほぼ「API から取得した明細・回答結果の非同期状態」であり、FutureProvider 系がそのまま該当する。riverpod_lint により誤用を静的検査に載せる |
| 毎晩の通知 | flutter_local_notifications | 通知は固定時刻・定型文であり、サーバー側の状態を参照しない。端末内スケジュールなら配信基盤という障害点を持たず、オフラインでも発火する。回答済みの夜の抑止も端末内で完結する |
| 認証 | firebase_auth + sign_in_with_apple + google_sign_in | デザイン要件定義が定めるサインイン方式（Apple / Google のみ）を Firebase Auth がネイティブ対応する |
| HTTP | http（標準パッケージ） | API は少数の JSON エンドポイントであり、インターセプタ等の追加機能を要しない |

### 端末側にデータベースを持たない

明細と回答結果は API から都度取得する。問答はサーバーが保持する確定値との突き合わせであり、オンラインであることが体験の前提のため、ローカルへの複製は同期という管理対象を増やすだけで利点がない。

## バックエンド

### Cloudflare Workers + TypeScript + Hono

API・メール受信・解析のすべてを Cloudflare Workers 上の TypeScript で実装する。ルーティングとミドルウェア（認証トークン検証を含む）は Hono を使う。Workers を選ぶ決め手はメール受信で、Email Routing + Email Workers により、転送されてきたメールを外部のメール受信サービスを介さずコードで直接受けられる。

### メール受信

独自ドメインの Cloudflare Email Routing でユーザー固有の転送先アドレスを受け、Email Worker に渡す。ユーザーは自身のメール環境で決済通知のみをこのアドレスへ転送する（要求定義「実績の自動取得」）。

### メール解析

決済事業者ごとの固定パーサ（正規表現／テンプレートマッチ）で店名・金額・日時を抽出する。実際に受信したメールをフィクスチャとしてテストに固定し、抽出の正しさをテストで保証する。対象の決済事業者と書式はドキュメントではなくパーサとフィクスチャで管理する。

LLM ではなく固定パーサとするのは次の理由による。

* 対象書式は利用者が使う決済事業者の少数の定型であり、決定論的に抽出できる
* 家計データを含むメール本文を外部の API に送らない。受け取るのは決済通知のみ・保持するのは店名・金額・日時のみというデータ最小化の方針と揃える
* 書式の知見がフィクスチャとテストというコードの形で蓄積される（選定方針の「守る資産」）

どのパーサにもマッチしないメールは原文を保持し、パーサ追加後に再処理できるようにする。

### データベース: D1 + Drizzle ORM

データは D1 に置く。スキーマとクエリは Drizzle ORM で定義し、スキーマとクエリの整合をコンパイル時に検証する。マイグレーション成果物は素の SQL ファイルであり、データモデルを他の SQL データベースへほぼそのまま持ち出せる（選定方針の「守る資産」）。

### 認証の検証

API は Firebase Auth が発行した ID トークンを Hono のミドルウェアで JWT 検証し、トークン内のユーザー ID で全クエリを絞る。ユーザー間のデータ隔離（要求定義「データの取り扱い」）はこの検証を通らない経路が存在しないことで満たす。

## 外部サービス

| サービス | 用途 | 範囲の限定 |
|---|---|---|
| Cloudflare | Workers / D1 / Email Routing | — |
| Firebase | Auth のみ | データは D1 に置くため、Firestore など他の機能は使わない |
| Apple Developer Program | TestFlight 配布、Sign in with Apple | — |
| 独自ドメイン | 転送先アドレスの受け皿 | Email Routing は MX を Cloudflare に向けたドメインを前提とするため必須 |

## 捕捉範囲

自動取得の対象は、利用のたびに即時の通知メールを発行する決済手段に限る。通知メールを持たない決済手段（コード決済、交通系 IC 等）は捕捉対象外とし、ズレとして現れた場合は補正入力（デザイン要件定義「補正」）で吸収する。要求定義は捕捉率を保証する仕組みを持たないと定めており、稀な利用の捕捉漏れはその想定の範囲内である。

## リポジトリ構成

単一リポジトリに役割別のディレクトリを並置する。

```
mobile/   Flutter アプリ
server/   Workers（API・Email Worker・パーサ）
docs/     ドキュメント
```

web フロントエンドとインフラ定義を導入する場合も、`web/`・`infra/` として同列に追加する。TypeScript のワークスペース機構は、TS パッケージが `server/` の1つである間は置かない。

## 検証コマンド

作業完了は次のコマンドの実行結果で判断する（CLAUDE.md「制約とコンテキストの置き場所」）。

| 対象 | コマンド | ツール |
|---|---|---|
| mobile | 静的検査 | flutter analyze + custom_lint |
| mobile | フォーマット | dart format |
| mobile | テスト | flutter test |
| server | 静的検査・フォーマット | Biome |
| server | テスト | Vitest |

server のテストは2層に分ける。バインディングに依存しない対象（パーサ、ハンドラの入力検証）は Hono の `app.request()` で通常の Vitest として実行し、D1・Email を実際に使う対象のみ @cloudflare/vitest-pool-workers で Workers ランタイム上で実行する。テストの大半を高速な前者に寄せるための分離である。
