# API 契約規約

## スコープ

本規約は、モバイルアプリとサーバーの境界で受け渡す値の表現と、両側のコードが共有する語彙を定義する。境界の両側が同じ1つの定義を参照するために、片側の規約ではなく独立した規約として置く。

アプリ内部の層構成は `.claude/rules/architecture/dart.md` が、サーバー内部の責務分割は `.claude/rules/architecture/typescript.md` が、技術スタックの選定理由は `docs/tech-selection.md` が定める。

以下は定義しない。

* エンドポイントの一覧と、個々のリクエスト・レスポンスの構造。実装とスキーマ・テストが担う（技術選定のスコープ定義に同じ）

## 用語

要求定義・デザイン要件定義が用いる日本語の概念と、コード・API・DB で使う識別子の対応を次のとおり固定する。

| 概念 | 識別子 | 指すもの |
|---|---|---|
| 明細 | expense | 決済通知1件から作られる支出の記録（店名・金額・日時） |
| 店 | merchant | 明細の店名。固定費の指定はこの単位で行う |
| 固定費 | fixedCost | 裁量支出から除外する指定。店に対して与える |
| 裁量支出 | discretionary | 固定費を除いた支出。問答の対象 |
| 回答 | answer | その日の裁量支出額としてユーザーが答えた推定額 |
| 実績 | actual | その日の裁量支出の合計 |
| ズレ | gap | 回答と実績の差 |
| 的中 | hit | ズレが判定の範囲に収まったこと |
| 連続回答日数 | streak | 連続して回答した日数 |
| 補正 | adjustment | 捕捉漏れを埋めるための手入力 |

同じ概念に複数の語を使わない。表にない概念を導入するときは、識別子を決める前に本表へ追加する。日本語のドキュメントと英語の識別子が1対1で対応していないと、要求定義の記述がコードのどこに対応するかを読み手が毎回推測することになるためである。

## 値の表現

* **金額は円の整数で表す**。JSON では number とし、小数を持たせない。2進浮動小数点は10進の金額を正確に表せないためである
* **日時は UTC の ISO 8601 文字列で表す**。タイムゾーン情報を持たない日時を境界で受け渡さない。パーサが読むメールの日時表記もアプリの表示時刻もローカル時刻であり、境界で正規化しないと同じ値が文脈により異なる時刻を指すためである
* **日付（どの日の問答か、どの日の明細か）は `YYYY-MM-DD` で表す**。日時を渡して受け側で日付に落とさない。落とす場所が2つあると、境界の解釈が両側で分岐するためである

## 1日の境界

1日の境界は Asia/Tokyo の 00:00 とする。明細をどの日に数えるか、連続回答日数が途切れたかの判定は、すべてこの境界による。

判定はサーバーでのみ行い、アプリは受け取った日付をそのまま扱う。両側に判定を置くと、端末のタイムゾーン設定によって同じ日の実績が食い違い、ズレが本人の感覚ではなく設定の差を示すことになるためである。

## エラー

* 予期される失敗（入力の検証エラー、認証の失敗）は HTTP のステータスコードで表す。200 に成功フラグを載せる形にしない
* エラーのボディは全エンドポイントで同一の構造とする

アプリ側は「通信・サーバーの失敗」と「画面の業務状態」を別の軸で扱う（`.claude/rules/architecture/dart.md`「画面状態の表現」）。失敗を 200 のボディで表すと、この2軸の振り分けが個々のエンドポイントごとの判断になる。

## 互換性

利用者が作者本人と友人1名である初期フェーズでは、API の後方互換を保たない。バージョン付けや旧形式への分岐を置かず、サーバーとアプリを同時に更新する。TestFlight 配布で全端末を更新できる規模であり、互換の維持は検証開始までの速度（技術選定「選定方針」）を下げるだけだからである。
