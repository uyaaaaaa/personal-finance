# TypeScript アーキテクチャ規約

## スコープ

本規約は `server/` 配下の TypeScript コードのアーキテクチャ（ディレクトリ責務・依存方向・不変条件）を定義する。コーディングの判断基準は `.claude/rules/coding/typescript.md` が、両側にまたがる決定（用語・1日の境界・API の互換性・生成物の扱い）は `.claude/rules/coding/common.md` が、技術スタックの選定理由は `docs/tech-selection.md` が定める。

API のエンドポイント定義とデータモデルの詳細は定義しない。zod スキーマと Drizzle スキーマ、およびテストが担う。

## ディレクトリ責務と依存方向

```
server/src/
  routes/       Hono のサブアプリ。ルート定義（zod スキーマ）とハンドラ
  middleware/   認証トークン検証と、ポート実装の組み立て
  domain/       モデル型・ポート・ユースケース。Hono にもバインディングにも依存しない
  parsers/      決済通知メールからの抽出。純粋関数
  db/           Drizzle スキーマと、ポートの実装（アダプタ）
```

エントリポイント（fetch ハンドラ・email ハンドラ）は `server/src/` 直下に置き、上記の合成のみを行う。

依存方向は次のとおりとする。

| 依存元 | 依存先 |
|---|---|
| domain | なし（標準ライブラリのみ） |
| parsers | なし（標準ライブラリのみ） |
| db | domain |
| routes | domain |
| middleware | domain, db |
| エントリポイント | すべて |

`routes` は `db` を import しない。永続化は domain が定義したポートを通じてのみ行う。

## ポートとアダプタ

```
domain/
  model.ts    ドメインの型。他のどこにも依存しない
  ports.ts    永続化のインターフェース。引数と戻り値は model.ts の型のみ
  <usecase>.ts  判定・計算。ポートを引数に取る
```

* ドメインのモデル型を単一の正とする。`db` のアダプタは Drizzle の行 → モデル型の変換を、`routes` はモデル型 → レスポンススキーマの変換を持つ
* ポートの引数と戻り値に Drizzle の型を現さない。ポートが実装の型を語ると、domain が実装を知らないという前提が名前だけになる
* `db` のアダプタは D1 の失敗をドメインの失敗へ翻訳する。Drizzle と D1 の例外型を domain より上へ通さない
* テストではポートのインメモリ実装を使う。D1 を実際に使うテストは、アダプタ自身とマイグレーションの検証に限る

型定義が Drizzle スキーマ・モデル型・zod スキーマの3箇所に現れるが、それぞれ DB の形・ドメインの形・境界の形という別の関心を表す。対応は変換関数のテストで固定する。DB のカラム名を変えたときに API の形が連動して動くことを避けるための分離である。

## 契約の生成

* ルートは `@hono/zod-openapi` の `createRoute` でスキーマとともに定義し、`app.openapi(route, handler)` で結合する
* リクエスト・レスポンスの構造と、そこに現れる値の表現は zod スキーマを唯一の正とする。同じ規定を文章の規約に置かない
* OpenAPI 仕様と Dart クライアントはこのスキーマから生成する（生成物の扱いは `.claude/rules/coding/common.md`）

境界の規定をスキーマに置くのは、それが決定論的に判定できる制約だからである（CLAUDE.md「制約とコンテキストの置き場所」）。文章の契約は両側の一致を検査できない。

## ハンドラの責務境界

* ハンドラはルート定義の直後にインラインで書く。別ファイルの関数へ切り出さない。切り出す必要があるときは `hono/factory` の `factory.createHandlers()` を使う。ハンドラを素の関数に切り出すとパスパラメータの型推論が失われるためである
* ハンドラは「検証済み入力の取り出し → ユースケースの呼び出し → レスポンスへの変換」のみを行う。判定・計算は `domain` が持つ

判定の分岐がハンドラに残ると、その検証には常に HTTP リクエストの組み立てが必要になり、分岐の数だけ遅いテストが増える。

## バインディングの到達範囲と実装の注入

* Workers のバインディング（D1・Email 等）に触れてよいのは、エントリポイントと middleware に限る
* middleware が `c.env` からポートの実装を組み立てて context に載せ、ハンドラはそれを取り出して使う。`routes` は `c.env` を読まない
* テストでの差し替えは、実装を context に載せる middleware を前置して行う。この前置を行うテストヘルパを1つに集約し、各テストが順序を組み立て直さないようにする。middleware の順序への依存が個々のテストに散ると、暗黙の前提になるためである

`routes` からバインディングを見えなくするのは、ハンドラの検証を Hono の `app.request()` で行えるようにするためである。`routes` が `c.env` を直接読むと、その検証は遅い側（@cloudflare/vitest-pool-workers）へ寄る。

## ルーティングの合成

* ルートはリソース単位の Hono サブアプリとして定義し、エントリポイントで `app.route()` により合成する
* 認証ミドルウェアは合成点で全ルートに適用する。認証不要のルートを設ける場合は、適用の外にあることがコードの構造から読み取れる形（ミドルウェア適用前の合成）に限る。既定を「認証あり」に倒すのは、適用漏れがデータ隔離の破れに直結するためである

## 認証の不変条件（HTTP 経路）

* ユーザー ID は、ミドルウェアが検証済みトークンから取り出して context に置いたものだけを使う。リクエストの path・query・body からユーザー ID を受け取らない
* ポートはユーザー ID を必須引数に取り、すべてのクエリをそれで絞る。ユーザーを横断するポートを定義しない

ユーザー間のデータ隔離（要求定義「データの取り扱い」）は「絞られないクエリ経路が存在しないこと」で満たす。絞り込みを呼び出し側の注意ではなくインターフェースの必須引数として固定するのは、このためである。

## 認証の不変条件（メール経路）

メール経路には検証済みトークンがなく、HTTP 経路の不変条件を適用できない。ユーザーの特定は次の2つを両方満たしたときに限る。

* **転送先アドレスとの完全一致**。ユーザーごとに推測困難なローカルパートを発行し、db に登録済みのアドレスとの完全一致でのみ解決する。アドレスの一部からの導出や前方一致で解決しない
* **送信元の検証**。送信元が登録済みの決済事業者ドメインであり、DKIM/SPF の検証に通っていること

転送先アドレスは秘密として扱う。ログ・エラーメッセージ・ドキュメント・フィクスチャに出さない。

いずれかを満たさないメールは明細を作らず、原文を保持する経路へ渡す。ユーザーの特定が転送先アドレスだけに依存すると、アドレスを知った第三者が他人の実績に偽の明細を注入でき、データ隔離が破れる。破棄せず保持するのは、判定の誤りを後から確認できるようにするためである。

## 明細の一意性

* 明細は、元になった決済通知メールから決まるキーで一意とする。同じメールを再び処理しても行が増えない形で書き込む
* 補正入力による明細は、メール由来の明細と区別できる形で保持する

メールは複数回処理されうる（転送経路の再送、パーサ追加後の再処理）。二重計上された実績は、ズレを本人の感覚ではなく処理の重複の指標に変え、問答そのものを成立させなくする（要求定義「ズレの即時提示」）。補正入力を区別するのは、再処理がユーザーの手入力を消さないためである。

## パーサの規約

* 1決済事業者 = 1パーサとし、パーサと同じ単位でフィクスチャを置く
* パーサは「メール文字列 → 抽出結果（店名・金額・日時）または未マッチ」の純粋関数とする。Hono・D1・バインディング・domain に依存しない。抽出ロジックの可搬性（技術選定「選定方針」）と、素の Vitest での検証のためである
* 未マッチは例外ではなく戻り値で表す。どのパーサにもマッチしないメールは原文を保持する経路へ渡し、破棄しない。パーサ追加後の再処理に必要なためである
* フィクスチャは実際に受信したメールを基とするが、実データ（店名・金額・日時・メールアドレス・氏名）は書式（桁区切り、日時形式、改行位置）を保ったままダミー値に置換してからコミットする。public リポジトリであり、家計の実データはコミットできないためである（CLAUDE.md「リポジトリ運用」）。書式を保つことが、フィクスチャが抽出テストとして機能する条件である

## Drizzle スキーマ変更の規約

* スキーマ変更は「Drizzle スキーマ定義の変更 → マイグレーション SQL の生成 → 両方をコミット」を1セットで行う
* 適用済みのマイグレーション SQL は編集しない。修正は新しいマイグレーションの追加で行う。マイグレーション SQL はデータモデルを他の SQL データベースへ持ち出すための可搬な成果物であり（技術選定「データベース」）、適用済みファイルの書き換えは適用履歴を環境間で分岐させる
* 命名は DB 側 snake_case、TypeScript 側 camelCase とし、対応は Drizzle のカラム定義で明示する。語そのものは `.claude/rules/coding/common.md`「用語」に従う

## 機械検査で固定する範囲

本規約のうち決定論的に判定できる項目は、文章ではなく検査で固定する（CLAUDE.md「制約とコンテキストの置き場所」）。

| 対象 | 固定の手段 |
|---|---|
| ディレクトリ間の依存方向（routes → db の禁止、domain の依存なし） | dependency-cruiser |
| domain・parsers が Hono・Drizzle・Workers の型に依存しないこと | dependency-cruiser と Biome の noRestrictedImports |
| クエリがユーザー ID で絞られること | ポートのシグネチャ（型検査） |
| リクエスト・レスポンスの値の表現 | zod スキーマ（実行時検証） |
| 明細の一意性 | スキーマの一意制約 |
| 生成物と入力の一致 | 再生成して差分が空であること |

依存規則の正は dependency-cruiser の設定に置く。Biome の `noRestrictedImports` は「どこから import したか」で分ける規則を持たないため、一律禁止の表現に限って併用する。検査は `server/` に最初のコードを置く時点で同時に用意する。検査を伴わない依存規約は、セッションをまたぐと守られないためである。
