# TypeScript アーキテクチャ規約

## ディレクトリ責務と依存方向

```
server/src/
  routes/       Hono のサブアプリとハンドラ。入出力変換のみ
  middleware/   認証トークン検証など、ルートを横断する処理
  parsers/      決済通知メールからの抽出。純粋関数
  db/           Drizzle スキーマとクエリ関数
```

エントリポイント（fetch ハンドラ・email ハンドラ）は `server/src/` 直下に置き、上記の合成のみを行う。

* 依存方向は routes → db、parsers → なし（標準ライブラリのみ）とする
* routes と parsers は互いに依存しない。メール受信の流れ（parsers の結果を db へ渡す）はエントリポイント側が合成する
* Workers のバインディングに触れてよいのは、エントリポイント・middleware・db のクエリ実行に限る

## ハンドラの責務境界

Hono のハンドラは「入力の検証・変換 → 関数の呼び出し → レスポンスの整形」のみを行う。判定・計算・解析のロジックは、バインディングに依存しない関数として routes の外に置く。これはテスト2層戦略の前提である。

## ルーティングの合成

* ルートはリソース単位の Hono サブアプリとして定義し、エントリポイントで `app.route()` により合成する
* 認証ミドルウェアは合成点で全ルートに適用する。

## 認証の不変条件

* ユーザー ID は、ミドルウェアが検証済みトークンから取り出して context に置いたものだけを使う。リクエストの path・query・body からユーザー ID を受け取らない
* db/ のクエリ関数はユーザー ID を必須引数に取り、すべてのクエリをそれで絞る。ユーザーを横断するクエリ関数を作らない

## パーサの規約

* 1決済事業者 = 1パーサとし、パーサと同じ単位でフィクスチャを置く
* パーサは「メール文字列 → 抽出結果（店名・金額・日時）または未マッチ」の純粋関数とする。Hono・D1・バインディングに依存しない。
* 未マッチは例外ではなく戻り値で表す。
* フィクスチャは実際に受信したメールを基とするが、実データは書式を保ったままダミー値に置換してからコミットする。

## Drizzle スキーマ変更の規約

* スキーマ変更は「Drizzle スキーマ定義の変更 → マイグレーション SQL の生成 → 両方をコミット」を1セットで行う
* 適用済みのマイグレーション SQL は編集しない。修正は新しいマイグレーションの追加で行う。
* 命名は DB 側 snake_case、TypeScript 側 camelCase とし、対応は Drizzle のカラム定義で明示する
