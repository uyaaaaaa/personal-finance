# TypeScript アーキテクチャ規約

## スコープ

本規約は `server/` 配下の TypeScript コードのアーキテクチャ（ディレクトリ責務・依存方向・不変条件）を定義する。コーディングの判断基準は `.claude/rules/coding/typescript.md` が、アプリとの境界で受け渡す値と語彙は `.claude/rules/architecture/api.md` が、技術スタックの選定理由は `docs/tech-selection.md` が定める。

API のエンドポイント定義とデータモデルの詳細は定義しない。実装とスキーマ・テストが担う（技術選定のスコープ定義に同じ）。

## ディレクトリ責務と依存方向

```
server/src/
  routes/       Hono のサブアプリとハンドラ。入出力変換のみ
  middleware/   認証トークン検証など、ルートを横断する処理
  domain/       判定・計算。Hono にもバインディングにも依存しない純粋関数
  parsers/      決済通知メールからの抽出。純粋関数
  db/           Drizzle スキーマとクエリ関数
```

エントリポイント（fetch ハンドラ・email ハンドラ）は `server/src/` 直下に置き、上記の合成のみを行う。

* 依存方向は routes → domain / db、middleware → db、domain → なし、parsers → なし（いずれも標準ライブラリのみ）とする
* routes と parsers は互いに依存しない。メール受信の流れ（parsers の結果を domain・db へ渡す）はエントリポイント側が合成する
* domain と parsers を純粋関数に保つのは、判定・計算・解析の検証を Workers ランタイムなしで書けるようにするためである

## バインディングの到達範囲

* Workers のバインディング（D1・Email 等）に触れてよいのは、エントリポイントと middleware に限る
* routes は `c.env` を読まない。middleware が context に載せた db ハンドルと検証済みユーザー ID だけを使う

routes からバインディングを見えなくするのは、ハンドラの検証を Hono の `app.request()` で行えるようにするためである。routes が `c.env` を直接読むと、その検証は遅い側（@cloudflare/vitest-pool-workers）へ寄る（技術選定「検証コマンド」）。

## ハンドラの責務境界

Hono のハンドラは「入力の検証・変換 → 関数の呼び出し → レスポンスの整形」のみを行う。判定・計算は `domain/`、永続化は `db/` が持ち、routes には残さない。

判定の分岐がハンドラに残ると、その検証には常に HTTP リクエストの組み立てが必要になり、分岐の数だけ遅いテストが増える。

## ルーティングの合成

* ルートはリソース単位の Hono サブアプリとして定義し、エントリポイントで `app.route()` により合成する
* 認証ミドルウェアは合成点で全ルートに適用する。認証不要のルートを設ける場合は、適用の外にあることがコードの構造から読み取れる形（ミドルウェア適用前の合成）に限る。既定を「認証あり」に倒すのは、適用漏れがデータ隔離の破れに直結するためである

## 認証の不変条件

* ユーザー ID は、ミドルウェアが検証済みトークンから取り出して context に置いたものだけを使う。リクエストの path・query・body からユーザー ID を受け取らない
* db/ のクエリ関数はユーザー ID を必須引数に取り、すべてのクエリをそれで絞る。ユーザーを横断するクエリ関数を作らない

ユーザー間のデータ隔離（要求定義「データの取り扱い」）は「絞られないクエリ経路が存在しないこと」で満たす。絞り込みを呼び出し側の注意ではなく関数シグネチャの必須引数として固定するのは、このためである。

## 明細の一意性

* 明細は、元になった決済通知メールから決まるキーで一意とする。同じメールを再び処理しても行が増えない形で書き込む
* 補正入力による明細は、メール由来の明細と区別できる形で保持する

メールは複数回処理されうる（転送経路の再送、パーサ追加後の再処理）。二重計上された実績は、ズレを本人の感覚ではなく処理の重複の指標に変え、問答そのものを成立させなくする（要求定義「ズレの即時提示」）。補正入力を区別するのは、再処理がユーザーの手入力を消さないためである。

## パーサの規約

* 1決済事業者 = 1パーサとし、パーサと同じ単位でフィクスチャを置く
* パーサは「メール文字列 → 抽出結果（店名・金額・日時）または未マッチ」の純粋関数とする。Hono・D1・バインディングに依存しない。抽出ロジックの可搬性（技術選定「選定方針」）と、素の Vitest での検証のためである
* 未マッチは例外ではなく戻り値で表す。どのパーサにもマッチしないメールは原文を保持する経路へ渡し、破棄しない。パーサ追加後の再処理に必要なためである
* フィクスチャは実際に受信したメールを基とするが、実データ（店名・金額・日時・メールアドレス・氏名）は書式（桁区切り、日時形式、改行位置）を保ったままダミー値に置換してからコミットする。public リポジトリであり、家計の実データはコミットできないためである（CLAUDE.md「リポジトリ運用」）。書式を保つことが、フィクスチャが抽出テストとして機能する条件である

## Drizzle スキーマ変更の規約

* スキーマ変更は「Drizzle スキーマ定義の変更 → マイグレーション SQL の生成 → 両方をコミット」を1セットで行う
* 適用済みのマイグレーション SQL は編集しない。修正は新しいマイグレーションの追加で行う。マイグレーション SQL はデータモデルを他の SQL データベースへ持ち出すための可搬な成果物であり（技術選定「データベース」）、適用済みファイルの書き換えは適用履歴を環境間で分岐させる
* 命名は DB 側 snake_case、TypeScript 側 camelCase とし、対応は Drizzle のカラム定義で明示する。語そのものは `.claude/rules/architecture/api.md`「用語」に従う

## 機械検査で固定する範囲

本規約のうち決定論的に判定できる項目は、文章ではなく検査で固定する（CLAUDE.md「制約とコンテキストの置き場所」）。

| 対象 | 固定の手段 |
|---|---|
| ディレクトリ間の依存方向、domain / parsers が標準ライブラリのみに依存すること | `src/` の import を走査するテスト |
| routes が `c.env` に触れないこと | 同上 |
| クエリがユーザー ID で絞られること | db/ のクエリ関数の必須引数（型検査） |
| 明細の一意性 | スキーマの一意制約 |
| 金額・日付の表現 | 型とスキーマ |

依存方向の検査は、`server/` に最初のコードを置く時点で同時に用意する。検査を伴わない依存規約は、セッションをまたぐと守られないためである。
