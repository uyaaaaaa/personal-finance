# TypeScript 規約

## スコープ

本規約は `server/` 配下の TypeScript コードについて、アーキテクチャ（ディレクトリ責務・依存方向・不変条件）と、機械検査で判定できないコーディングの判断基準を定義する。技術スタックの選定理由は `docs/tech-selection.md` が定める。

以下は定義しない。

* 機械判定できる規約。「機械検査が担う範囲」に挙げるツールが担う
* API のエンドポイント定義とデータモデルの詳細。実装とスキーマ・テストが担う（技術選定のスコープ定義に同じ）

## アーキテクチャ規約

### ディレクトリ責務と依存方向

```
server/src/
  routes/       Hono のサブアプリとハンドラ。入出力変換のみ
  middleware/   認証トークン検証など、ルートを横断する処理
  parsers/      決済通知メールからの抽出。純粋関数
  db/           Drizzle スキーマとクエリ関数
```

エントリポイント（fetch ハンドラ・email ハンドラ）は `server/src/` 直下に置き、上記の合成のみを行う。

* 依存方向は routes → db、parsers → なし（標準ライブラリのみ）とする
* routes と parsers は互いに依存しない。メール受信の流れ（parsers の結果を db へ渡す）はエントリポイント側が合成する
* Workers のバインディング（D1・Email 等）に触れてよいのは、エントリポイント・middleware・db のクエリ実行に限る

### ハンドラの責務境界

Hono のハンドラは「入力の検証・変換 → 関数の呼び出し → レスポンスの整形」のみを行う。判定・計算・解析のロジックは、バインディングに依存しない関数として routes の外に置く。

これはテスト2層戦略（技術選定「検証コマンド」）の前提である。ロジックがハンドラ内やバインディング依存の関数に書かれると、その検証が遅い側（@cloudflare/vitest-pool-workers）へ寄ってしまう。

### ルーティングの合成

* ルートはリソース単位の Hono サブアプリとして定義し、エントリポイントで `app.route()` により合成する
* 認証ミドルウェアは合成点で全ルートに適用する。認証不要のルートを設ける場合は、適用の外にあることがコードの構造から読み取れる形（ミドルウェア適用前の合成）に限る。既定を「認証あり」に倒すのは、適用漏れがデータ隔離の破れに直結するためである

### 認証の不変条件

* ユーザー ID は、ミドルウェアが検証済みトークンから取り出して context に置いたものだけを使う。リクエストの path・query・body からユーザー ID を受け取らない
* db/ のクエリ関数はユーザー ID を必須引数に取り、すべてのクエリをそれで絞る。ユーザーを横断するクエリ関数を作らない

ユーザー間のデータ隔離（要求定義「データの取り扱い」）は「絞られないクエリ経路が存在しないこと」で満たす。絞り込みを呼び出し側の注意ではなく関数シグネチャの必須引数として固定するのは、このためである。

### パーサの規約

* 1決済事業者 = 1パーサとし、パーサと同じ単位でフィクスチャを置く
* パーサは「メール文字列 → 抽出結果（店名・金額・日時）または未マッチ」の純粋関数とする。Hono・D1・バインディングに依存しない。抽出ロジックの可搬性（技術選定「選定方針」）と、素の Vitest での検証のためである
* 未マッチは例外ではなく戻り値で表す。どのパーサにもマッチしないメールは原文を保持する経路へ渡し、破棄しない。パーサ追加後の再処理に必要なためである
* フィクスチャは実際に受信したメールを基とするが、実データ（店名・金額・日時・メールアドレス・氏名）は書式（桁区切り、日時形式、改行位置）を保ったままダミー値に置換してからコミットする。public リポジトリであり、家計の実データはコミットできないためである（CLAUDE.md「リポジトリ運用」）。書式を保つことが、フィクスチャが抽出テストとして機能する条件である

### Drizzle スキーマ変更の規約

* スキーマ変更は「Drizzle スキーマ定義の変更 → マイグレーション SQL の生成 → 両方をコミット」を1セットで行う
* 適用済みのマイグレーション SQL は編集しない。修正は新しいマイグレーションの追加で行う。マイグレーション SQL はデータモデルを他の SQL データベースへ持ち出すための可搬な成果物であり（技術選定「データベース」）、適用済みファイルの書き換えは適用履歴を環境間で分岐させる
* 命名は DB 側 snake_case、TypeScript 側 camelCase とし、対応は Drizzle のカラム定義で明示する

## コーディング規約

### 機械検査が担う範囲

| ツール | 担う範囲 |
|---|---|
| Biome（recommended） | lint とフォーマット |
| tsconfig strict | 型検査 |

これらで判定できる項目を本規約には書かない。決定論的に判定できる規約を新たに設けるときは、本文への追記ではなく lint ルール・型・テストでの表現を選ぶ（CLAUDE.md「制約とコンテキストの置き場所」）。

### 値の表現

* 金額は円の整数として扱う。浮動小数点数にしない。2進浮動小数点は10進の金額を正確に表せないためである
* 明細の日時は UTC に正規化して保存する。タイムゾーン情報を持たない日時をコンポーネント間で受け渡さない。パーサが読むメールの日時表記とアプリの表示時刻はいずれもローカル時刻であり、境界で正規化しないと同じ値が文脈により異なる時刻を指すためである

### エラーの扱い

予期される失敗（パーサの未マッチ、入力の検証エラー）は戻り値で表し、例外は予期しない障害に限る。予期される失敗を戻り値の型に載せることで、処理漏れを型検査で検出するためである。

### テスト方針

* バインディングに依存しない対象（パーサ、ハンドラが呼ぶ関数、入力検証）は、素の Vitest と Hono の `app.request()` で検証する
* @cloudflare/vitest-pool-workers を使うのは、D1・Email を実際に使う対象に限る
* 新しいロジックは、まずバインディング非依存の形で書けないかを検討する。テストの大半を高速な層へ寄せるためである（技術選定「検証コマンド」）
