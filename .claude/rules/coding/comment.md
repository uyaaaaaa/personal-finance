# コメントの規約

## スコープ

本規約は `mobile/`・`server/` 配下のコードと設定ファイルに書くコメントについて、書かないものと書いてよいものを定義する。`*.md`（ドキュメント・rules・SKILL.md）の記述内容は `.claude/skills/documentation/SKILL.md` が定める。

`@ts-expect-error`・`biome-ignore`・Dart の `// ignore:` `// ignore_for_file:` はコメントの形をしたコードであり、本規約の対象外とする。要否と記述形式は各リンタの設定が担う。

コメントの要否は決定論的に判定できず lint で表現できないため、文章の規約として置く（CLAUDE.md「制約とコンテキストの置き場所」）。

原則としてコメントは書かず、コードを読めば分かることはコードで表現する。コメントは実装と同時には更新されず、いずれ実装から乖離するためである。乖離したコメントは無いより有害であり、判断に迷うものは書かない側に倒す。

## 書かないもの

| 種類 | 例 | 理由 |
|---|---|---|
| コードの言い換え | `// 明細を日付で並べ替える` を `sortByDate(entries)` に付ける | 直下のコードが同じことを言っている |
| セクションラベル | `// ---- Providers ----`、`// ビルド` | 直後の宣言名で分かる |
| 型・シグネチャで分かること | `/// 明細の ID` を `final String id` に付ける、`@param amount 金額` | 型と名前が正であり、二重管理になる |
| リポジトリ内を読めば分かる背景 | `// 金額は円の整数で扱う` | 規約・型・テストが持っている |
| 他ファイルの場所案内 | `// 認証の検証はミドルウェアで行っている` | grep で分かる。参照先が動いた瞬間に嘘になる |
| 処理ブロックの要約 | `// 明細を月ごとにまとめて新しい順に並べる` | 関数名・変数名で表現する |
| コメントアウトされたコード | `// await repository.save(entry);` | git 履歴が持っている |
| ツール由来の定型コメント | scaffold が残す設定ファイル冒頭のドキュメント URL | 生成物の残骸である |
| 変更履歴・課題 ID | `// 2025-09 追加`、`// (ABC-123)` | git 履歴と課題管理が持っている |

## 書いてよいもの

以下に当てはまる場合のみ書く。

### 外部の仕様・都合

リポジトリ内を全部読んでも分からず、外部の知識が要るもの。決済事業者のメール書式、ライブラリやプラットフォームの挙動、外部サービスの制約が該当する。

```ts
// 事業者Aの通知メールは金額欄に全角数字を使う
const normalizeDigits = (text: string) => ...
```

### 一見不要に見えるコードが必要な理由

消してよさそうに見える行を、次の人が消さないためのもの。

```dart
// 画面復帰時に再取得しないと、補正入力の結果が古いまま表示される
ref.invalidate(entriesProvider);
```

### 意図的に書いていないこと

コードに現れないため、コメントでしか表現できないもの。

```dart
// 状態の出し分けは AsyncValue.when に統一しているため、ここで null 判定はしない
```

### 名前から意味が読み取れない値

```ts
// 例: "AMAZON.CO.JP*A1B2C3" -> "AMAZON.CO.JP", "ｾﾌﾞﾝ-ｲﾚﾌﾞﾝ" -> "セブン-イレブン"
```

## 書き方

* 「何を」ではなく「なぜ」を書く。ただし書くのは、リポジトリ内を読んでも分からない「なぜ」に限る
* 1〜2行に収める。それ以上の説明を要するものは、コードコメントではなく `docs/` に書く
* 実装を変えたらコメントも直すか消す。残す価値が無くなったら消す

## 判定手順

以下のいずれかなら書かない。

1. コードから読み取れなくなる情報が無い
2. その情報の正を規約・型・テスト・`docs/` が持っている
3. 命名・定数の抽出・関数の分割で表現できる（表現する）

残ったもののうち「書いてよいもの」に当てはまるものだけを書く。
