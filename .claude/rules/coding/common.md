# 共通規約

## スコープ

本規約は `mobile/` と `server/` の双方に適用される、言語に依存しない判断基準と、両側にまたがる決定を定義する。言語ごとの基準と、その言語で機械検査が担う範囲は `.claude/rules/coding/dart.md` および `.claude/rules/coding/typescript.md` が定める。

API のリクエスト・レスポンスの構造と、そこに現れる値の表現は定義しない。`server/` の zod スキーマが唯一の正であり、そこから生成された OpenAPI 仕様と Dart クライアントが従う（`.claude/rules/architecture/typescript.md`「契約の生成」）。

ドキュメント（`*.md`）の記述規約は `.claude/skills/documentation/SKILL.md` が定める。本規約はコードのみを対象とする。

## 用語

要求定義・デザイン要件定義が用いる日本語の概念と、コード・API・DB で使う識別子の対応を次のとおり固定する。

| 概念 | 識別子 | 指すもの |
|---|---|---|
| 明細 | expense | 決済通知1件から作られる支出の記録（店名・金額・日時） |
| 店 | merchant | 明細の店名。固定費の指定はこの単位で行う |
| 固定費 | fixedCost | 裁量支出から除外する指定。店に対して与える |
| 裁量支出 | discretionary | 固定費を除いた支出。問答の対象 |
| 回答 | answer | その日の裁量支出額としてユーザーが答えた推定額 |
| 実績 | actual | その日の裁量支出の合計 |
| ズレ | gap | 回答と実績の差 |
| 的中 | hit | ズレが判定の範囲に収まったこと |
| 連続回答日数 | streak | 連続して回答した日数 |
| 補正 | adjustment | 捕捉漏れを埋めるための手入力 |

同じ概念に複数の語を使わない。表にない概念を導入するときは、識別子を決める前に本表へ追加する。日本語のドキュメントと英語の識別子が1対1で対応していないと、要求定義の記述がコードのどこに対応するかを読み手が毎回推測することになるためである。

## 1日の境界

1日の境界は Asia/Tokyo の 00:00 とする。明細をどの日に数えるか、連続回答日数が途切れたかの判定は、すべてこの境界による。

判定はサーバーでのみ行い、アプリは受け取った日付をそのまま扱う。両側に判定を置くと、端末のタイムゾーン設定によって同じ日の実績が食い違い、ズレが本人の感覚ではなく設定の差を示すことになるためである。

## API の互換性

利用者が作者本人と友人1名である初期フェーズでは、API の後方互換を保たない。バージョン付けや旧形式への分岐を置かず、サーバーとアプリを同時に更新する。TestFlight 配布で全端末を更新できる規模であり、互換の維持は検証開始までの速度（技術選定「選定方針」）を下げるだけだからである。

## 命名

* ドメインの概念を指す識別子は本規約「用語」の対応に従う。表にない語を新たに作らない
* 同じ概念を指すのに複数の語を使わない

## コメント

* コメントは、**コードから読み取れない理由**（なぜその実装なのか、なぜ他の方法を採らないのか）に限って書く
* 処理内容の言い換えを書かない。コードが持つ情報を二重に持つと、片方だけが更新される
* 変更の記録（「〜に変更」「元は〜だった」）、レビュー・会話・PR への参照を書かない。git 履歴が担うためである
* 型・関数名で表現できることをコメントで補わない。補う必要があるなら、名前か型を直す

## 残さないもの

* 使われていないコード、到達しない分岐、コメントアウトされたコード。復元は git 履歴が担う
* 実装しないまま残す TODO コメント。実装するか、やらないと決めるかのいずれかにする
* 利用者が1つしかない抽象化。共通化は2つ目の利用者が現れてから行う。想定で作った抽象は、2つ目が現れたときに形が合わない

## 生成物の扱い

生成物とは、別の定義から機械的に導かれるコードを指す（zod スキーマから導く OpenAPI 仕様と Dart クライアント、Drizzle のマイグレーション SQL、コード生成器の出力）。

* 生成物はコミットする。クローン直後に検証スクリプトが通る状態を保つためである
* 生成物を手で編集しない。編集が必要なら、生成の設定か入力側のスキーマを直す
* 生成物が入力と一致していることは、再生成して差分が空であることで検査する。文章の規約にしない
* 生成物は lint とフォーマットの対象外とする。整形の責務は生成器にあり、検査を通すための手編集は上の禁止と衝突するためである

## 変更の範囲

依頼された変更に付随しない整形・改名・移動を、同じコミットに混ぜない。差分が変更の意図を表さなくなり、レビューで本体の変更を読み分けられなくなるためである。

## 依存の追加

パッケージの追加は、標準ライブラリと既存の依存で実現できないことを確認してから行う。追加したパッケージは用途と選定理由を `docs/tech-selection.md` に記録する。依存は検証の結果に応じて捨てる判断の対象であり（技術選定「選定方針」）、選んだ理由が残っていないと捨ててよいかを判断できないためである。
