# 共通コーディング規約

## スコープ

本規約は、`mobile/` と `server/` の双方に適用される、言語に依存しないコーディングの判断基準を定義する。言語ごとの基準と、その言語で機械検査が担う範囲は `.claude/rules/coding/dart.md` および `.claude/rules/coding/typescript.md` が定める。

ドキュメント（`*.md`）の記述規約は `.claude/skills/documentation/SKILL.md` が定める。本規約はコードのみを対象とする。

## 命名

* ドメインの概念を指す識別子は `.claude/rules/architecture/api.md`「用語」の対応に従う。表にない語を新たに作らない
* 同じ概念を指すのに複数の語を使わない

## コメント

* コメントは、**コードから読み取れない理由**（なぜその実装なのか、なぜ他の方法を採らないのか）に限って書く
* 処理内容の言い換えを書かない。コードが持つ情報を二重に持つと、片方だけが更新される
* 変更の記録（「〜に変更」「元は〜だった」）、レビュー・会話・PR への参照を書かない。git 履歴が担うためである
* 型・関数名で表現できることをコメントで補わない。補う必要があるなら、名前か型を直す

## 残さないもの

* 使われていないコード、到達しない分岐、コメントアウトされたコード。復元は git 履歴が担う
* 実装しないまま残す TODO コメント。実装するか、やらないと決めるかのいずれかにする
* 利用者が1つしかない抽象化。共通化は2つ目の利用者が現れてから行う。想定で作った抽象は、2つ目が現れたときに形が合わない

## 変更の範囲

依頼された変更に付随しない整形・改名・移動を、同じコミットに混ぜない。差分が変更の意図を表さなくなり、レビューで本体の変更を読み分けられなくなるためである。

## 依存の追加

パッケージの追加は、標準ライブラリと既存の依存で実現できないことを確認してから行う。追加したパッケージは用途と選定理由を `docs/tech-selection.md` に記録する。依存は検証の結果に応じて捨てる判断の対象であり（技術選定「選定方針」）、選んだ理由が残っていないと捨ててよいかを判断できないためである。
