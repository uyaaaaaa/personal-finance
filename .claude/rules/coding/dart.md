# Dart / Flutter コーディング規約

## スコープ

本規約は `mobile/` 配下の Dart コードについて、機械検査で判定できない Dart 固有のコーディングの判断基準と、機械検査が担う範囲の宣言を定義する。

## 機械検査が担う範囲

| ツール | 担う範囲 |
|---|---|
| flutter_lints | Effective Dart 準拠の静的検査 |
| riverpod_lint（custom_lint 経由） | Riverpod の誤用検出 |
| dart format | フォーマット |

これらで判定できる項目を本規約には書かない。決定論的に判定できる規約を新たに設けるときは、本文への追記ではなく lint ルールの追加で表現する（CLAUDE.md「制約とコンテキストの置き場所」）。

`lib/api/` の生成物は上記の対象外とする。

## Riverpod の慣習

* Provider 名は `xxxProvider` サフィックスとする
* build メソッド内では `ref.watch`、コールバック内では `ref.read` を使う

## 値の表現

境界の表現はサーバーの zod スキーマが定め、生成クライアントの型がそれを写す。アプリ内部では次に従う。

* 金額は `int`（円）で扱う。`double` にしない
* 日時は UTC の `DateTime` として保持し、ローカルへの変換は表示の直前に行う。UTC とローカルの `DateTime` を同じ変数・同じフィールドに混在させない。`DateTime` は型でどちらかを区別せず、二重変換が実行時にも現れない
* 「どの日か」はサーバーが返した日付をそのまま使い、端末側で日時から導出しない

## エラーの扱い

* 通信の失敗・サーバーのエラーは例外として送出し、AsyncValue のエラー相へ載せる。Provider の中で握りつぶして空データに倒さない。失敗と「明細が0件」が同じ表示になると、捕捉漏れを確認するという明細一覧の役割（要求定義「明細への導線」）が成立しない
* 業務上ありうる分岐（回答前、明細が0件）は例外ではなく型で表す
* 認証エラーは個々の Provider で扱わない。`core/` の interceptor が受ける

## テスト方針

* **unit test**: Flutter に依存しない判定・計算。純粋 Dart の関数として分離されていることが前提となる
* **widget test**: 状態と表示の対応（排他的状態の出し分け、結果表示の構成要素）。Provider は override で差し替える

振り分けの基準は「レンダリング結果の検証が必要か」のみとする。widget test は unit test より遅く、ロジックの回帰検出を寄せると検査全体が遅くなる。

生成された API クライアントそのものを対象とするテストは書かない。契約との一致は再生成の差分が空であることで足りる。テストの対象は、クライアントを使う側（Provider、interceptor）に限る。
