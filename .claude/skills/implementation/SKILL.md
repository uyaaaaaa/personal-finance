# 実装の判断順序

## 原則

最も良いコードは、書かれずに済んだコードである。ただし短さは理解の後に来る。要求と、それが触れる既存コードを読み、実際の流れを端から端まで辿る。辿り終えてからラダーを上から評価し、**最初に成立した段で止める**。

理解を省いて得た小さな差分は、効率ではなく2つ目の不具合である。

## ラダー

1. **作らずに済むか**。要求に含まれない先回りの機能は作らない
2. **このリポジトリに既にあるか**。既存の関数・型・ポート・ウィジェットを使う。数ファイル離れた場所にあるものの再実装が、最も多い無駄である
3. **標準ライブラリで足りるか**（Dart の `core`・`intl`、TypeScript の Web 標準 API）
4. **プラットフォームの機能で足りるか**。DB の制約・索引・ウィンドウ関数をアプリケーションコードで代替しない。zod の検証を手書きの分岐で代替しない。Flutter の標準ウィジェットを自作ウィジェットで代替しない
5. **既に入っている依存で足りるか**。新規追加の可否は `.claude/rules/coding/common.md`「依存の追加」による
6. **1行で書けるか**
7. ここまで成立しなければ、**動く最小のコードを書く**

2つの段が同時に成立するなら、上の段を採って先へ進む。動く最初の案を採用してよい。

同じ大きさの選択肢が2つあるなら、境界値で正しいほうを採る。最小化の対象はコード量であり、アルゴリズムの正しさではない。

## 不具合の修正

報告されるのは症状であって原因ではない。触ろうとしている関数の呼び出し元をすべて grep し、共有されている1箇所を直す。報告された経路だけに条件を足すと、同じ関数を呼ぶ他の経路が壊れたまま残る。呼び出し元ごとに同じ条件を置くよりも、共有点の1つの条件のほうが差分は小さい。

例外は、`server/src/parsers/` のように「1決済事業者 = 1パーサ」と分離が規定されている箇所である。この単位を跨いで共通化しない。

## 最小化しない領域

次は短さを理由に削らない。

* 信頼境界での入力検証（zod スキーマ、パーサの未マッチの表現）
* ユーザー ID の取り扱い（`.claude/rules/architecture/typescript.md`「認証の不変条件」）
* 1日の境界の判定をサーバーに置くこと（`.claude/rules/coding/common.md`「1日の境界」）
* 記録を失わせないエラー処理
* アクセシビリティ
* 明示的に要求されたもの。利用者が完全な版を求めたなら、それを作る

## 検査を伴わない実装は未完成

分岐・ループ・解析・金額計算を含むロジックには、それが壊れたときに落ちる最小の検査を1つ残す。置き場所は `.claude/rules/coding/typescript.md`・`.claude/rules/coding/dart.md` のテスト方針による。1行で自明なコードに検査は要らない。

## 出力

コードを先に出す。説明は「省いたもの」と「それを足す条件」を最大3行とする。説明がコードより長いなら、説明を削る。単純化を弁護する段落は、散文に姿を変えた複雑さである。

形式: `[コード] → 省いた: X。必要になる条件: Y。`

要求された説明（レポート、手順の解説）はこの制限の対象外とする。
