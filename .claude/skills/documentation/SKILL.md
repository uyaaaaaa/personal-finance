# ドキュメント作成規約

## スコープ

本規約は、リポジトリ内のすべての `*.md` の**記述内容**を定義する。README、`docs/` 配下のドキュメント、`CLAUDE.md`、`.claude/` 配下の `SKILL.md` および rules を含む。

以下は定義しない。

* ファイル配置とディレクトリ構成。どのカテゴリをどこに置くかは `CLAUDE.md`「制約とコンテキストの置き場所」が定める
* ADR(設計判断の記録)。ADR は決定時点の判断を残す記録であり、検討した代替案と却下理由を含めてはじめて機能する。本規約の「経緯を書かない」原則とは目的が相反するため、同じ規約で扱わない

## 原則

ドキュメントは、**最終的な設計を最初からそう計画していたものとして記述する**。

想定読者は、検討の経緯を一切知らない新規参画者とする。経緯を知らなければ意味が通じない文を残してはならない。

更新時は差分を追記するのではなく、**その時点の最終形として全面的に書き直す**。結果として、ドキュメントは常に「現時点の仕様のスナップショット」であり、そこに至る過程の記録ではない。

## 書かないもの

* 変更履歴・経緯(「〜を追加した」「当初は〜だったが」「〜から変更」)
* 検討過程(「〜も検討したが見送った」「議論の結果」)
* 会話・会議・レビューへの参照(「前回の指摘により」「相談の結果」)
* 課題管理ツールのID参照(タスクID、チケット番号)
* 未確定であることの但し書き(「暫定」「後で決める」)。未確定なら、確定させるか、その項目自体を書かない

## 書くもの

* 決定された仕様そのもの
* **その決定を選んだ理由**

理由は経緯ではない。「なぜこの設計なのか」は新規参画者が同じ判断を再現するために必要な情報であり、必ず書く。

書いてよい理由と、書いてはならない経緯の違いは、時系列への依存の有無で判断する。

| 可 | 不可 |
|---|---|
| 変更種別を2区分に留めるのは、計画外の割り込みを分離することがフロー診断上もっとも効くためである | 当初は4区分だったが、議論の結果2区分に集約した |
| 判定は変更ファイルのパスから機械的に行う。人手の付与を伴わない | 手動付与案はレビューで却下された |

## 構造

* 各ドキュメントは冒頭にスコープ(何を定義し、何を定義しないか)を明記する
* 上位・下位の関係を持つドキュメントは、冒頭で上位文書を参照する
* スコープ外の項目は、どこが担うかとあわせて明示する
